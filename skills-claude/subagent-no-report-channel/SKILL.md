# subagent-no-report-channel

## Problem

You spawn several subagents, brief each to `SendMessage` its results back, and
then receive nothing. They emit idle notifications. `ListAgents` shows them
alive. Minutes pass. The obvious reading is that they are wedged, and the
obvious response -- kill and respawn -- **throws away completed work**.

Two distinct causes produce identical silence:

1. **No messaging tool in the agent type's toolset.** An agent definition
   declares its tools. If a messaging tool is not among them, the agent
   physically cannot report. It will try, get "No such tool available" or
   "disabled for this session", and (correctly) stop rather than retry blindly.
2. **A forward-only wrapper agent.** Some agent types exist to dispatch work to
   a separate background job runtime and are explicitly scoped **not** to poll
   status or fetch results. Such an agent will hand off the job, report that
   fetching the outcome is outside its role, and end its turn. That is the agent
   behaving as designed, not failing.

In both cases the work is done or in flight, and the result is sitting somewhere
you have not looked.

## The oracle: transcript, not idle signals

**Idle notifications are generated by the runtime, not sent by the agent.** They
are therefore *not* evidence that the agent's own outbound send succeeded. Do not
read them either way.

The reliable liveness test is the agent's transcript: a `tool_use` block with no
matching `tool_result` means the agent is genuinely blocked mid-call. Zero
dangling calls means it is **not** wedged.

Transcripts live under `~/.claude/projects/<cwd-slug>/<session-uuid>.jsonl`, one
per agent. The slug is the working directory with separators replaced. Find the
recent ones:

```bash
find ~/.claude/projects -name '*.jsonl' -mmin -20
```

Then apply the oracle, and read the tool count at the same time -- a completed
review with 19 tool calls and an abandoned start with 1 look identical from
outside:

```bash
python3 - <<'PY'
import json, sys
path = sys.argv[1] if len(sys.argv) > 1 else 'transcript.jsonl'
uses, results = {}, set()
for line in open(path):
    try:
        d = json.loads(line)
    except ValueError:
        continue
    content = (d.get('message') or {}).get('content')
    if isinstance(content, list):
        for b in content:
            if b.get('type') == 'tool_use':
                uses[b['id']] = b.get('name')
            elif b.get('type') == 'tool_result':
                results.add(b.get('tool_use_id'))
dangling = {k: v for k, v in uses.items() if k not in results}
print('tool_uses:', len(uses), 'dangling:', len(dangling), list(dangling.values())[:5])
PY
```

Read it as:

| dangling | tool count | meaning |
|---|---|---|
| > 0 | any | genuinely blocked mid-call -- the only real wedge |
| 0 | high | finished the work; look for stranded output |
| 0 | very low (1-3) | ended early; read its final text for the reason |

## Recovery 1 -- the result is in the agent's final text

An agent that cannot send will very often put its entire result in its final
response instead, especially if briefed to. Extract the last assistant text:

```bash
python3 - <<'PY'
import json, sys
texts = []
for line in open(sys.argv[1]):
    try:
        d = json.loads(line)
    except ValueError:
        continue
    m = d.get('message') or {}
    if m.get('role') != 'assistant':
        continue
    content = m.get('content')
    if isinstance(content, list):
        for b in content:
            if b.get('type') == 'text' and b.get('text', '').strip():
                texts.append(b['text'])
print(texts[-1] if texts else 'no assistant text')
PY
```

In the run this skill came from, one agent's complete review -- findings,
verdict, and three explicitly-rejected false positives -- was sitting in that
final block, prefixed with a note that the send tool had errored.

## Recovery 2 -- the result is in a background job runtime

A forward-only wrapper hands off to a job runtime and prints a task id. Those
jobs persist their own state and results on disk, independent of the agent.
For plugin-hosted runtimes the shape is:

```
~/.claude/plugins/data/<plugin>/state/<session>/jobs/<task-id>.json
~/.claude/plugins/data/<plugin>/state/<session>/jobs/<task-id>.log
```

Find the record by task id rather than guessing the path:

```bash
grep -rl "<task-id-fragment>" ~/.claude/plugins/data 2>/dev/null
```

Then read status and result. The useful fields are `status`, `completedAt`, and
`result` (whose payload is often under a `rawOutput` key):

```bash
python3 - <<'PY'
import json, sys
d = json.load(open(sys.argv[1]))
print('status:', d.get('status'), '| completed:', d.get('completedAt'))
r = d.get('result')
print(r.get('rawOutput') if isinstance(r, dict) else r)
PY
```

The jobs completed normally in the case this came from -- `status: completed`,
full findings in `rawOutput`. Nothing needed re-running.

## Read the sandbox caveats in the recovered output

Recovered job output frequently ends with a note about what the job could **not**
do -- no network, no writable path, an engine that could not initialize. Those
notes materially change how much the result is worth, and they are invisible if
you only read the findings.

In the source run, three of four jobs reported that the independent engine never
started because the read-only sandbox denied it. The reviews were still useful,
but the cross-engine independence the whole design was chosen for **did not
happen**, and saying so was part of reporting the result honestly.

## Prevention

- **Check the agent type's declared tools before briefing it to report.** If the
  definition lists only an execution tool, no messaging brief will ever work.
- **Always give a fallback instruction**, regardless: *"If the send fails, do not
  retry blindly -- put your complete result in your final response text and
  stop."* This costs one sentence and converts a total loss into recovery 1.
- **Instruct against fabrication explicitly.** Every agent in the source run
  refused to invent findings it did not have and said plainly where it stopped.
  That is what made the silence diagnosable instead of misleading.
- **Know that addressing is directional.** A spawned teammate does not address
  its parent by the parent's peer-session name; there is a distinct role address
  for the parent. The authoritative value is echoed back on any outbound message
  the parent sends (look for the sender/routing field in the tool result) -- read
  it there rather than assuming a name works in both directions. Briefing agents
  with the wrong reply address produces exactly the same silence as having no
  send tool at all, which is why the transcript oracle comes first.
