# Search Backend Phrase Verification

> **Canonical source.** This skill lives in the repo at
> https://github.com/voitta-ai/skillz (file:
> `skills/search-backend-phrase-verification/SKILL.md`). Updates go through the
> repo's worktree + PR workflow.

## Problem

Search APIs advertise operator support loosely. A backend may accept
`"an exact phrase"` and `site:example.com`, return a confident page of results,
and have honoured neither — matching the *topic* instead. Nothing in the
response says so.

If a pipeline is built on exact-phrase retrieval, that failure is invisible and
it corrupts every conclusion drawn downstream. Two opposite symptoms both
mislead:

- **Plausible but wrong results.** The queried phrase is absent from every
  document. Whatever selects or scores those documents then looks broken, or
  looks like it is telling you the content does not exist.
- **Zero results.** A quoted phrase that is not also a *topic* can match
  nothing at all, which reads as "nobody writes this" when it means "this
  backend cannot find a phrase."

The expensive version of this mistake is concluding that an approach is
structurally unworkable, writing that up, and acting on it — when the only
thing that was broken was the measuring instrument.

## Context / Trigger Conditions

Reach for this before trusting any negative result from a search-sourced
pipeline, and specifically when:

- Results share a subject with the query but do not contain its quoted text.
- A rare, diagnostic phrase returns a suspiciously round number of results
  (a full page) — a phrase that rare should return few or none.
- Some quoted phrases return a full page and others return zero, with no
  pattern that makes sense as a fact about the corpus.
- A `site:`-scoped query returns a different document type than intended
  (profiles instead of posts, category pages instead of articles).
- You are about to write "the content isn't there" or "this can't be found by
  keyword" in an issue, a report, or a decision.

## Solution

### 1. Pick a diagnostic phrase

Choose a phrase that is **rare, literal, and not a topic**. Good: a
first-person construction (`"I own a"`, `"we decided to"`), an idiosyncratic
turn of phrase. Bad: anything that doubles as a subject heading, because a
topic match and a phrase match are then indistinguishable — which is the whole
thing you are testing.

### 2. Measure the hit rate, do not eyeball it

Run the query, take the returned documents, fetch each one, and test for the
**literal string**. Report it as a fraction.

```python
hits = 0
for result in results[:n]:
    body = fetch(result.url).lower()
    present = phrase.lower() in body
    hits += present
    print(f"  phrase_present={present} {result.title[:60]}")
print(f"{hits} of {n} documents contain the phrase the backend was asked to match.")
```

Check the fetched document, not the snippet. A snippet is generated by the
backend and may be built to look responsive; some corpora also serve a
boilerplate description to crawlers, so the snippet can be identical on every
result regardless of content.

### 3. Read the result honestly

- **0 of n** — the backend does not honour phrases here. Every prior
  conclusion that rested on phrase retrieval is void, including the negative
  ones.
- **n of n** — phrases are honoured. A zero-result query is now evidence about
  the corpus.
- **Mixed** — partial or best-effort matching. Treat phrase presence as a
  filter you apply yourself, after retrieval, not as something the query bought
  you.

### 4. Swap the instrument and re-measure the *same* metric

If the backend fails, re-run the identical queries through a different one and
compare the metric you actually care about — not just the hit rate.

This step is what makes the eventual answer trustworthy, and it cuts both ways:

- The metric moves → the original conclusion was an artefact. Rewrite it.
- The metric does **not** move, while retrieval demonstrably improved → the
  negative is now sound, and far stronger than before, because the obvious
  confound has been eliminated rather than argued away.

Hold the rest of the pipeline fixed across the swap. Changing the backend and
the selection criteria together tells you nothing about either.

### 5. Separate the two questions in the write-up

State retrieval and selection as independent findings: how much was found, and
how much of it qualified. Collapsing them into one verdict is what hides an
instrument failure, and it is also what makes a sound negative look like a
guess.

## Verification

You have done this properly when you can state, with numbers:

- the hit rate of the diagnostic phrase on each backend tried;
- documents retrieved per backend, same queries;
- how many met the downstream bar, per backend;
- and therefore whether the limiting factor is retrieval or selection.

If you cannot fill in all four, you are not yet entitled to a conclusion either
way.

## Example

A pipeline searched a large social corpus for posts containing specific
first-person complaints, scoped with `site:` and quoted phrases. Results were
topically right and never contained the phrase; one query shape returned a full
page while a near-identical one returned nothing. The first conclusion drawn was
that the corpus did not contain the content and the approach was dead.

The diagnostic phrase `"I own a"` returned 18 results. Six were fetched and
checked: **0 of 6** contained the string. A second backend, same query:
**10 of 10**. So the diagnosis had been about the backend.

Re-running every query through the phrase-honouring backend took retrieval from
1 document to 80. The share meeting the downstream bar stayed at **zero**, with
the ceiling moving from "nothing retrieved" to well under half the required
threshold. The original verdict survived — but now as a sound negative about
the corpus rather than a measurement artefact, and with the actual limiting
factor correctly named.

Had only the first half been done, the write-up would have blamed the corpus.
Had only the second, a reviewer could reasonably have asked whether better
retrieval would change the answer. Both halves are needed.

## Notes

- **Operator support is per corpus, not per API.** A backend that honours
  phrases on the open web may not on a `site:`-scoped subset, where it may be
  serving a thinner index. Verify in the configuration you will actually ship.
- **A zero from an unverified backend is not evidence.** It is the single
  easiest way to conclude that something does not exist.
- **Scope operators deserve the same check.** Confirm the returned URLs match
  the intended shape; a `site:` restriction narrowed by path is often applied
  loosely, and a mismatch is sometimes a useful finding in its own right rather
  than only a bug.
- **Re-verify after a backend or plan change.** This is an empirical property
  of a service, not a contract, and it can change without notice.
- **Budget the check, not the campaign.** Verification is one query and a
  handful of fetches. It is orders of magnitude cheaper than the work built on
  an unvalidated assumption, and cheaper still than retracting a conclusion.
